# 01-05 review: API permissions and draft security

**Integrated later:** this note records the review as it ran. Where the [integration note](01-05-integration.md) differs, the integration note wins.

**Scope:** independent threat-model review for [task 01-05](../../roadmap/phases/01-discovery-foundation/05-architecture-contracts.md) of the editor boundary, protected document meta, Content API, API keys, cache, and preview. **Status: recommendations.** Nothing here is owner approval, and no product API exists. The proofs are throwaway code in [`spikes/01-05-contracts/api`](../../../spikes/01-05-contracts/api/README.md). The stable result is the [API contract](../../contracts/api/README.md).

## Conclusion

The direction of the plan holds: a separate module, protected meta, hashed keys, published-only reads, authenticated preview. All of it was enforceable on real WordPress 7.1.4 and 7.0.8. The plan as written was still wrong or silent in two serious places, and WordPress defaults undo several of its stated rules unless a route actively counters them:

- The auth callback proved in 01-02 opens `_blixis_document` to read and unvalidated write through XML-RPC (F1).
- A single `_blixis_document` value has no place for a draft edit of a published page, so saving is publishing (F2).

## Assets, actors, and trust boundaries

**Assets:** unpublished content and draft edits of live pages; the raw document; publication state; API key secrets; WordPress sessions and nonces; site availability.

**Actors:** anonymous visitor; subscriber; default author (no page capabilities); page author, owner and non-owner (`edit_pages`, `edit_published_pages`); page publisher without `edit_others_pages`; editor; administrator; API client holding a key, which is not a WordPress user; another plugin on the same site; a shared cache or CDN; a reverse proxy.

| Boundary | Crossing | Control |
|---|---|---|
| Browser to editor routes | Cookie and nonce | Post-specific capability, page-only guard |
| Live document to draft edit | Autosave to publish | Per-user autosave revision; `edit_post` and `publish_pages` to promote |
| Protected meta to generic paths | REST, XML-RPC, admin AJAX | `show_in_rest: false` and `auth_callback` returning false |
| Internet to Content API | Bearer key or anonymous mode | Transport check, key check, status allowlist, field allowlist |
| WordPress identity to Content API | Cookie, nonce, application password | Discarded: ignored for authorization and visibility, rendering runs logged out |
| Origin to shared cache | Response headers | Per-class `Cache-Control`, `Vary`, no user data in public responses |
| Proxy to origin | Forwarded headers | Honoured only from a configured peer |

## Findings

Severity is for the planned design if built as written. Reproduce with `spikes/01-05-contracts/wordpress/run.sh api`; `OBSERVED` names below are printed lines in that output. `OBSERVED` lines reproduced on both tested combinations. Results from early runs and mutations are from 7.1.4 only and are marked as such.

### High

**F1. The 01-02 meta shape exposes the document through XML-RPC.** `auth_callback => user_can(edit_post)` makes `edit_post_meta` true for protected meta, which is what the XML-RPC custom-field path relies on. `show_in_rest: false` does not apply there. A page author can read the document through `wp.getPost` and change it through `wp.editPost` `custom_fields`, skipping server validation and the renderer's input guarantees.
*Reproduce:* `xmlrpc_01_02_auth_callback_shape_readable_by_page_author = true`, `..._writable_without_validation = true`. An isolated mutation that gave `_blixis_document` this callback failed 21 checks: 18 reads plus update, add, and delete.
*Fix:* `auth_callback => '__return_false'`. Trusted routes write with `update_post_meta()`, which checks no capability. Checks confirm byte-exact revision capture and restore still work. On Multisite (v1.1), super admins bypass this; retest there.

**F2. Saving a live page is publishing.** `ARCHITECTURE.md` has one document value per page and says autosave never publishes, but gives draft edits of a published page no location. The 01-02 PUT route writes the live value for anyone with `edit_post`, so a role with `edit_published_pages` and no `publish_pages` would change public content. That was read from the 01-02 code and not run against a live page.
*Fix, proven here:* PUT on a `publish`, `future`, or `private` page returns `409 blixis_use_autosave`. Draft edits go to the user's autosave revision with `update_metadata()`, because `update_post_meta()` redirects a revision ID to its parent. `POST /publish` needs `edit_post` and `publish_pages`, and promotes only the caller's own autosave.

### Medium

**F3. Plain `WP_Query` is a privilege-confusion trap.** With no explicit status, an admin sees private pages (`naive_wp_query_admin_shows_private = true`, anonymous `false`). A plugin widening `pre_get_posts` shows drafts to anonymous callers (`..._with_widening_plugin_shows_draft = true`). The proof uses prepared SQL plus a PHP re-check per post, and it holds against the same plugin. Phase 08 should not rely on `WP_Query` here.

**F4. Core sends permissive CORS on every REST route.** `core_routes_reflect_any_origin_with_credentials = ["https://evil.example.test","true"]`. "CORS is not authorization" is correct, but the allowlist in API.md does nothing until `rest_send_cors_headers` is removed for the namespace.

**F5. Core overrides the error contract and query rules.** Measured on an unguarded fixture route (`core_control_params_on_unguarded_route`): `_envelope` turns a 404 into HTTP 200, `_jsonp` wraps the body, `_fields` removes fields, including a contract version field if a route had one, and `_method` changes the method. Route matching is case-insensitive, so `/wp-json/BLIXIS-FIXTURE/V1/...` still reaches the route and a case-sensitive prefix check would miss it. A bad cookie nonce or unknown route gets a core error body. Handling this took four hooks: `rest_api_init`, `rest_authentication_errors`, `rest_post_dispatch`, `rest_pre_serve_request`. An early 7.1.4 run also failed the no-store check on a bad nonce until the suppressing filter moved above core's priority.

**F6. `permission_callback` runs twice per request.** `rest_send_allow_header` calls it again to build `Allow`. An early 7.1.4 run with a limit of 3 returned `[200,200,429,429,429]` instead of `[200,200,200,429,429]`, and audit lines doubled. Callbacks with side effects need that filter removed for the namespace or must be idempotent. A check now confirms one audit line per request.

**F7. WordPress cannot enforce a rate limit by itself.** With limit 10 and 60 parallel requests, transients allowed more than 10 in every run: 12 to 21 across runs (`transient_limit_10_...`). `wp_cache_incr()` stayed at 1 across requests on a default install. One atomic SQL upsert allowed exactly 10 each time, at the cost of a database write per request and a custom table. All of this runs after PHP and WordPress have loaded, so it is a quota and not DoS protection. Volumetric defence must sit at the edge. A persistent object cache was not tested.

**F8. One namespace for all modules blurs the boundary.** API.md uses `blixis/v1`, and nothing separates editor routes. Independently deployable modules with one namespace share the namespace index, and a broad own-route rule could catch the wrong routes. The proof uses `blixis/v1` (public), `blixis-editor/v1` (Blocks), and `blixis-admin/v1` (keys).

### Low

**F9. Core preview is no-store but not noindex.** `core_preview_headers_only` shows `no-store` with no `X-Robots-Tag` and no robots meta tag. ADR-005 needs an explicit rule. Exposure is limited, because only logged-in users see the content. A draft opened without `preview=true` is equally affected; the proof covers both.

**F10. A fresh nonce can enter a public response.** Core sends `X-WP-Nonce` after a valid nonce. On a plain route, core's nocache header also applies, so it is not publicly cached (`naive_public_route_...` shows the nonce with `no-store`; my first assumption that it would be `public` was wrong). The risk appears only once an API suppresses nocache to give logged-in callers the same cache policy, as this contract does. Whoever suppresses nocache must also remove the nonce. The proof does both.

**F11. The uniform 404 covers this API only.** `core_enumeration_draft_vs_missing = [401,404]`: `/wp/v2/pages/{id}` still distinguishes a draft from a missing ID. The contract should not claim site-wide protection. Recommendation: accept this, since IDs are not secrets and no content leaks.

**F12. Argument validation runs before `permission_callback`.** Anonymous bad input gets `400`, not `401` (`anonymous_invalid_args_...`). Validators must not read objects or reveal state. Content routes declare no `args` and validate inside the gate.

**F13. `edit_published_pages` alone changes live `post_content` through core** (`edit_published_pages_lets_core_...= true`). That is WordPress's meaning of the capability, not a bug. Blixis should not grant it without `publish_pages` in any role it defines.

**F14. Discovery.** The site index lists Blixis namespaces and the key admin route (`site_index_lists_key_admin_route = true`). No key material appears. Use `show_in_index => false` for the admin and editor routes. The `blixis/v1` index stays public.

**F15. A published child discloses a draft parent's slug through `link`** (`published_child_link_... = true`). WordPress's public URL does the same. Documented in the contract.

**F16. Smaller plan corrections.** `X-Powered-By` exposes the PHP version on `/health` unless removed. A gate calling `wp_set_current_user(0)` would log out internal `rest_do_request()` callers, so the proof zeroes the user only on real HTTP requests and restores it after rendering. `VERSION_CONFLICT` has no use in a read-only API. "Element metadata" on a public `/schema` is an unnecessary fingerprint, so the contract leaves it out.

### Not findings: confirmed by test

Anonymous, subscriber, default author, and other-author denial; missing and wrong nonce; `publish_pages` and `edit_post` both required; autosave cannot publish, including with `status=publish`; no document on any registered GET route for anonymous or admin; every hidden state byte-identical to a missing ID, headers included; admin cookie, nonce, and application password change nothing; all invalid key classes indistinguishable; no plaintext in any table or log; a stale ETag gets `404` after unpublishing; a stolen preview URL shows nothing of the edit (`403` anonymous); draft edits of a live page reach no public route.

## Decisions recorded by this review

**Bearer key and WordPress identity.** The key never hooks `determine_current_user`. It sets a request-scoped client and leaves the user at 0, proven by a whoami probe; with no `/wp/v2` access, editor access, or key administration. An application password does log in a user, so on content routes it is ignored and in keyed mode gets `401`. Key administration refuses application passwords, so a leaked one cannot mint keys.

**HTTPS behind a proxy.** `is_ssl()`, or the direct peer on an explicit list and `X-Forwarded-Proto: https`. Spoofed headers from any other peer were refused. The list is exact-match in the proof; a product needs CIDR. The common `wp-config.php` snippet that trusts the header unconditionally defeats this undetectably, so it must be a documented installation rule.

**Unknown query parameters are refused, not ignored.** This gives clear client errors and prevents cache-key pollution. Alternative: ignore silently, which is friendlier but lets `?x=1` bust caches and hides a client's mistaken `status=draft`.

**Rejected key alternatives.** Application passwords: they log in a full user. JWT or OAuth: much more machinery for read-only server clients. Plain SHA-256: adequate for a 256-bit secret, but with a keyed hash a database dump alone cannot be used to test a candidate key. The proof derives its HMAC key from `wp_salt('secure_auth')`. Rotating salts therefore invalidates all keys, and on a site with no salt constants the salt sits in the database, removing the benefit. That fallback was reasoned, not tested.

**Key storage.** One non-autoloaded option per key avoids read-modify-write loss on a shared list. A custom table is the likely product choice once usage metadata is needed.

## External review links: evaluated, not built

If later approved, a link needs all of the following:

- A token of at least 32 CSPRNG bytes; stored only as a keyed hash with an ID.
- Bound to one post and one revision. An edit or publish invalidates it.
- A default TTL of 24 hours, maximum 7 days; revocation per link and per post.
- Its own route, never the public route or Content API. Rendered logged out, with no nonce and no editor assets.
- `no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, and no third-party scripts, since a URL token leaks through referrers, logs, and history. Exchanging the token for a short-lived cookie and redirecting reduces that.
- Rate limits on failed attempts; key-ID-only audit; tests for each rule.

Costs are a new unauthenticated path to unpublished content, a token store, a revocation interface, and a cache-bypass rule per host. Recommendation: Q06 stays authenticated-only for the MVP. The honest limit: WordPress has no view-only draft capability, so a reviewer account today must be able to edit that page. A view-only review role would need a capability mapping that this review did not design or test, though it looks cheaper than links. Reopen when a real client review is blocked by login.

## Recommended status

These are recommendations for the owner.

| Item | Recommendation | Main alternative | Consequence |
|---|---|---|---|
| ADR-001, API part | Keep Accepted (provisional), amend: API module owns `blixis/v1`, keys, and its limits; it only reads posts and calls a versioned renderer interface; it never writes documents; separate namespaces | One plugin with Blocks: simpler, but deploys the public API and editor together | The API needs a defined behaviour when Blocks is inactive, which is not yet designed or tested |
| ADR-005 | Accept, amended: authenticated preview, no-store and noindex on any non-public view, draft edits in per-user autosave revisions | External links now: higher risk and cost, see above | Reviewers need accounts |
| ADR-007 | Accept, amended: keyed hash, key is a client and not a user, HTTPS rule above, atomic quota, edge for volume | Application passwords: rejected above | Needs a key UI, a rate table or edge, and salt-rotation documentation |
| Q06 | Authenticated-only for MVP | External links | As above |
| Q10 | Read-only in v1 | Writes: would need the whole editor validation and publish model on a second surface, with no stated consumer | Clients change content in WordPress |
| Q11 | Authenticated by default, anonymous by explicit configuration | Public by default: simple, but publishes everything to any scraper, and is hard to retract | Slightly harder setup for public sites; response has 60-second shared-cache staleness in anonymous mode |

## What was tested and exact results

Environment: macOS arm64, Docker Desktop 29.8.2, `wordpress/run.sh` disposable stack, MariaDB 11.4.13, PHP built-in server over plain HTTP, 2026-11-06.

| Command, from `spikes/01-05-contracts` | Result |
|---|---|
| `wordpress/run.sh api` (WordPress 7.1.4, PHP 8.4) | `CONTRACT_RESULT pass=2281 fail=0` |
| `wordpress/run.sh api 7.0.8 8.5` | `CONTRACT_RESULT pass=2269 fail=0` |
| `npx -y pnpm@12.18.0 run test` | 11 pass, 0 fail |
| `run typecheck`, `run lint`, `run format:check` | Exit 0 |
| `php -l` on each proof file | No syntax errors |

The matrix expands to 546 real HTTP requests. The exposure sweep sends 788 requests on 7.1.4 (152 registered routes) and 764 on 7.0.8 (148 routes), which explains the difference in totals. The 12 fewer checks on 7.0.8 are all in the sweep, whose route count differs. Median 404 time for draft and missing IDs was about 10 to 11 ms in each case; that is a measurement with no statistical test, not a proof of no timing channel.

**Mutation check, on 7.1.4.** Eight deliberate breaks in one run produced 692 failed checks: no status check, nonce kept, Allow callback kept, core CORS kept, revocation ignored, 01-02 meta shape, no `publish_pages`, no noindex. Each break had at least one matching failed check. The combined run masked the XML-RPC write checks, because the publish break had already published the draft, so the meta shape was also run alone, with 21 failures. Two weak checks found during this review were replaced: the admin AJAX check now has an unprotected-key contrast, and the sweep has a `show_in_rest` positive control.

## Gaps

- **Real TLS and a real proxy were not tested.** The harness is plain HTTP, and proxy behaviour was simulated with headers from `127.0.0.1`.
- **Apache and FPM may strip `Authorization`.** The built-in server passes it. A product must also read `REDIRECT_HTTP_AUTHORIZATION` and test on real hosts.
- **Real CDN behaviour, purge, and persistent object caches** were not tested. The headers are correct by RFC 9111 reading only.
- **Multisite and super admins** were not tested. Planned for v1.1.
- **WXR export** was not tested. It likely includes the document for users with `export`, normally administrators, which should be checked in phase 08.
- **Memory-exhaustion fatals** bypass the `Throwable` guard. Only thrown errors, SQL errors, and warnings were injected.
- **Failed key attempts** have no per-address limit in the proof. A 256-bit secret makes guessing useless, but the attempts still cost CPU.
- **Rendering** uses `the_content`, not the planned allowlisted renderer. HTML safety belongs to the document review.
- **Token changes:** a body-hash ETag changes only if the HTML changes. `SECURITY_AND_PERFORMANCE.md` asks for caching by token version, so if `html` depends on tokens, the render cache key must include it. To resolve with the tokens review.
- **Blocks inactive:** the behaviour of the API then is undesigned.
- **Load testing** was not done. The API p95 budget remains unmeasured.
