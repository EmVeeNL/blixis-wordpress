# Token contract version 2 and renderer contract version 1

**Status: token contract version 2 is the shipped contract (task 03-06 Part B, [owner decisions](../../roadmap/phases/03-child-theme-setup-wizard/06-token-driven-themes.md#owner-decisions) 1 to 4). Version 1 was the accepted baseline from task 01-05 and stays in [`v1/`](v1/) as frozen migration input and for the renderer fixtures; the renderer is not implemented.** The validators, stylesheet generator, and theme.json projection are implemented in Blixis Blocks and `packages/tokens` (tasks 02-03, 03-02, 03-03, 03-05, 03-06); the renderer is not. See the [review note](../../architecture/reviews/01-05-tokens.md) for the 01-05 evidence and gaps. Its hex-only colour rule (decision 7 of the [01-05 integration note](../../architecture/reviews/01-05-integration.md)) is superseded by this version.

## What changed in version 2

| Area | Version 1 | Version 2 |
|---|---|---|
| `schemaVersion` | 1 | 2. A stored or submitted version 1 config is validated under the version 1 rules and migrated (see [Migration](#migration)) |
| Colours | Hex only | Hex, `rgb()`, `hsl()`, `oklch()`. The stored value keeps the format entered |
| Dark palette | None | Optional `colorsDark` with the same five names as `colors` |
| Units | `px`, `rem` everywhere | `px`, `rem` everywhere; `em` for the type scale and spacing; `%`, `ch`, `vw` for `layout.contentWidth` and `layout.wideWidth` only |
| Slider ranges | In the interface only | Per field and unit in the contract: `fields` in the token map |
| Site setting | None | `blixis_color_scheme`: `system` (default), `light`, `dark` |

## Validation rules

Order: size (64 KiB), depth (8, measured on raw bytes), JSON parse, `config.not_object`, schema version, then fields. A missing, wrongly typed, or unsupported `schemaVersion` stops validation. Otherwise all errors are returned, sorted by UTF-8 bytes of `path`, then `code`. Paths are RFC 6901 pointers; the root is `""`.

Names are closed: an unknown key is `field.unknown`, so a config cannot name a token without a compiled utility. Every section and key is required except `colorsDark`, and defaults belong to the wizard, not the validator. Hex colours are lower-cased and short hex is expanded, so spelling does not change the hash; the other colour formats keep the entered text.

A conforming implementation must also:

- decode to a form that distinguishes `{}` from `[]` (PHP: object mode, not `assoc`);
- make `$` strict (PCRE: the `D` modifier), or `"#fff\n"` passes;
- treat `1.0` as the integer 1;
- reject lone surrogates and keys starting with NUL (PHP refuses them, `JSON.parse` does not);
- measure depth before parsing (PHP reports a syntax error on very deep input);
- use ASCII classes for digits and letters. Non-ASCII font names are refused in v1 and v2.

## Colours

Each colour in `colors`, `colorsDark`, and inside `shadows` is one of four formats, in the modern space-separated syntax only. The format is part of the stored value: an `oklch()` colour is never converted to hex, because that can lose colours outside sRGB. The stylesheet and `theme.json` carry the value unchanged.

| Format | Grammar | Component ranges |
|---|---|---|
| Hex | `#rgb`, `#rrggbb`, `#rrggbbaa` (any case; stored lower-case, six or eight digits) | |
| RGB | `rgb(R G B)` or `rgb(R G B / A)`; R, G, B all numbers or all percentages | numbers 0 to 255, percentages 0% to 100% |
| HSL | `hsl(H S% L%)` or `hsl(H S% L% / A)` | H 0 to 360 (no unit), S and L 0% to 100% |
| OKLCH | `oklch(L C H)` or `oklch(L C H / A)` | L 0 to 1 or 0% to 100%, C 0 to 0.5 (a number), H 0 to 360 (no unit) |

Alpha `A` is a number 0 to 1 or a percentage 0% to 100%. Numbers have no sign, no leading zero (`0.5`, not `.5` or `00.5`), no exponent, up to three integer digits and six decimals. Rejected: comma-separated legacy syntax, `rgba()` and `hsla()`, upper-case function names, `deg` units, `none`, extra or missing spaces, named colours, `color()`, `color-mix()`, `var()`, `calc()`, `oklab()`. Component ranges are checked by both validators after the pattern matches; an out-of-range colour fails with `token.color.invalid` like any other bad colour. The ranges live in `colorRanges` in the token map.

### Contrast

Contrast checks convert to sRGB internally; they never change the stored value. The helper (`contrastRatio()` in `@blixis/tokens`, `contrast_ratio()` in PHP) returns the WCAG 2 ratio from 1 to 21. A translucent background is composited over white, then a translucent foreground over that, in gamma-encoded sRGB as browsers do. An `oklch()` colour outside the sRGB gamut is clipped: it is converted to linear sRGB and each channel is clamped to 0 to 1. Both implementations agree to 1e-9 on every colour in every valid fixture.

### Dark palette

`colorsDark` is optional. When present it has the same five names as `colors` and every one is required (a partial palette is `field.required` per missing name). A `colorsDark` key in a version 1 config is `field.unknown`.

- **Stylesheet.** Without `colorsDark` the output is as in version 1. With it, `--blixis-color-*` take their light values in `:root` and their dark values under `@media (prefers-color-scheme: dark)`, and `:root` gets `color-scheme: light dark`.
- **Site setting.** The option `blixis_color_scheme` is `system` (default: follow the visitor), `light` (ignore the dark palette, `color-scheme: light`), or `dark` (dark values in `:root`, no media query, `color-scheme: dark`). Without a dark palette the setting changes nothing. There is no visitor toggle. Saving needs the `edit_theme_options` capability; an unknown value is refused (`blixis_scheme_invalid`, status 400) and a missing capability is `blixis_scheme_forbidden` (403). A change purges page caches through `blixis_tokens_changed`.
- **theme.json.** With `colorsDark`, the palette presets are `var(--blixis-color-<slug>)` instead of literal values, so blocks follow the switch; without it they stay literal.
- **Preview.** `previewProperties(config, map, "dark")` returns the dark colours (the light ones when the config has no dark palette).

## Units and slider ranges

| Field group | Units | Grammar name |
|---|---|---|
| `typeScale`, `spacing` | `px`, `rem`, `em` | `lengthEm` |
| `radius`, `layout.gutter` | `px`, `rem` | `length` |
| `layout.contentWidth`, `layout.wideWidth` | `px`, `rem`, `%`, `ch`, `vw` | `lengthWidth` |
| `shadows` offsets, blur, spread | `px`, `rem` | inside `shadow` |
| `motion` durations | `ms` | `duration` |

A bare `0` is allowed everywhere. A unit a field does not allow fails with the field's usual error (`token.length.invalid`). The token map's `fields` object gives, for every length and duration token, its grammar, its `units`, a `defaultUnit`, and a slider `ranges` entry per unit: `{ "min", "max", "step" }`. `shadowControls` gives the ranges for the shadow editor (offset, blur, spread in `px`; opacity 0 to 1). The ranges guide the wizard controls; the validators check the grammar, not the range, so a stored value outside a slider range stays valid. Defaults and fixture values sit inside the ranges (a test enforces it).

## Migration

`schemaVersion` 2 is the current version. `migrate_config()` (PHP) and `migrateConfig()` (TypeScript) are pure functions that bring a config that already passed validation at its own version up to the current one, one version at a time. Version 1 to 2 changes only the version number, because every version 1 value is a valid version 2 value and everything new is optional or widens a grammar.

- **A version 1 config is validated under the version 1 rules**, not the wider version 2 rules: hex colours only, `px` and `rem` only, no `colorsDark`. Every version 1 fixture keeps its verdict and error list (a test runs them all through both validators). The result is then migrated, so a valid version 1 input yields a normalized version 2 config. `legacyVersions` in the token map holds the version 1 grammars.
- **On read**, `store_read()` revalidates the stored config (migrating it) and checks the stored hash against the config as it was written, then returns the migrated config with its new hash. The stored row is not rewritten by a read, so a read never loses data or changes the revision.
- **On save**, `store_write()` validates and migrates the incoming bytes and migrates the replaced config that becomes `previous`, so a save leaves no older version in the row. Rollback of a stored version 1 `previous` goes through the same validator.
- Version 3 and later, or a non-integer version, is `schema.version_unsupported`.

Cache keys: `blixis:css:c2:g2:{configHash}`; when a dark palette is set and the scheme is not `system`, the key ends in `:slight` or `:sdark`. The config hash covers `colorsDark`, so a palette change changes the key. Drafts and unauthorized previews still have no key.

## Breakpoints

`breakpoints` must equal `breakpointPreset` (`sm` 40rem, `md` 48rem, `lg` 64rem, `xl` 80rem). They are a build input, never emitted to runtime CSS or `theme.json`. A runtime value cannot work: `var()` is not allowed in a media query, the query never matches, and Tailwind 4.3.5 writes such a query without any warning. Any other value fails with `token.breakpoint.not_preset`; changing the preset means a rebuild and a new contract version.

## Generation

The PHP generator is the single production generator, because the only runtime on a WordPress host is PHP and saves are validated there. `tokens/src/generate.ts` is a test oracle that proves the bytes are reproducible; do not ship it. The admin preview sets `--blixis-*` values with `style.setProperty` from `token-map.json` after local validation, and the server result stays authoritative.

The WordPress Site Editor is not a token source. Its user-origin settings must not override a Blixis token; task 03-05 must enforce and test this policy.

Delivery on a public page: `wp_theme_json_data_theme` merges the [`theme.json` data](v1/golden/default.theme.json), and an inline `blixis-tokens` style carries the [CSS](v1/golden/default.tokens.css). Values are literal in both, and a parity test compares them with WordPress's actual output. Font sizes need `fluid: false`; slug `2xl` becomes `--wp--preset--font-size--2-xl`.

Tailwind: use [`golden/tailwind.css`](v1/golden/tailwind.css). It imports utilities only (no preflight, no cascade layer) and uses `@theme inline`. Load it after global styles. Never add stored content as a `@source`: arbitrary values such as `bg-[url(javascript:alert(1))]` compile.

## Persistence

Store one autoloaded option, `blixis_theme_config`, holding JSON: `revision`, `hash`, `config`, `previous`. The colour scheme is a separate option, `blixis_color_scheme`. Write it with one compare-and-swap `UPDATE`, then call `wp_clean_theme_json_cache()`. `update_option` has no compare-and-swap, and writing an option alone leaves global styles stale. Revalidate on read and check the hash; a bad row falls back to `previous`, then to Base presets. Apply only when `theme.slug` is the active stylesheet. Export is the normalized config; import goes through the same validator.

## Cache keys

| Key | Form | Invalidated by |
|---|---|---|
| CSS | `blixis:css:c{contract}:g{generator}:{configHash}[:s{scheme}]` | Config value, generator, contract, colour scheme (only with a dark palette) |
| HTML fragment | `blixis:html:p{post}:d{documentHash}:v{renderer}:{registryHash}` | Stored document bytes, renderer, registry |
| Full page | fragment key plus `:{configHash}` | All of the above |

Element HTML holds class names only, so a token value change leaves it byte-identical; a test proves it. Pages embed the CSS and must be purged, through the `blixis_tokens_changed` action. Drafts, private, pending, future, and password-protected posts have no key: the functions return null.

## Renderer

Output comes from the registry only. Classes come from tables, never from input. Text is plain text: escape with `esc_html( str_replace( '&', '&amp;', $text ) )`, because `esc_html` and `esc_attr` otherwise keep existing entities and the page would differ from the React preview. URLs must match `urlPattern` first, then pass `esc_url( $url, $protocols )`; `esc_url` alone admits `//evil.test` and `ftp:`. Version 1 has no rich-text field: a `paragraph.html` prop is `render.unknown_prop` here and `forbidden_prop` in the [document contract](../document/README.md). Inline formatting later arrives as structured marks through an element version bump.

An unknown type or version renders nothing and leaves stored data untouched. Diagnostics are returned out of band and require `edit_post`; they never enter HTML, because HTML is cacheable and public.

Hook `the_content` after every core filter and check `post_password_required()` first. An earlier hook executes shortcodes in user text and rewrites it. A later hook without the check publishes password-protected documents.

## Responsive resolution

Each breakpoint takes its own override, otherwise the nearest lower value, otherwise the base value in `props`. A class is emitted only where the resolved value changes. Absent means inherit, and order in the input does not matter. Parity between React and PHP is compared on parsed DOM, because their bytes legitimately differ (`&#039;` and `&#x27;`). Device preview must use an iframe: media queries follow the viewport, not a wrapper's width.

## Reproduce

The version 2 token files are derived from two scripts in `packages/tokens`. After changing the contract:

```bash
cd packages/tokens
node scripts/build-contract.ts     # token-map.json (contract and both shipped copies) and the schema
node scripts/gen-fixtures.ts       # new fixtures, expected errors, goldens from the PHP code, migrations
pnpm run test
```

`build-contract.ts --check` fails when a derived file is stale; the tests run it. The original 01-05 proof of version 1 is reproduced from `spikes/01-05-contracts` (`node tokens/scripts/gen-fixtures.ts`, `gen-golden.ts`, `sync-bundle.ts`, then `pnpm run test`). A changed golden is a contract change. Review it; do not regenerate to make a test pass.
