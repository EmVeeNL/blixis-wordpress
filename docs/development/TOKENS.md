The [setup wizard](SETUP_WIZARD.md) (task 03-03) stores configurations; task 03-05 applies them, previews drafts, and rolls back, as described below.

## Code

| Part | Location | Role |
|---|---|---|
| Server validator | `plugins/blixis-blocks/inc/tokens/validate.php` | `validate_bytes()` returns a normalized config or sorted `{code, path}` errors. Authoritative. `migrate_config()` is the pure version step |
| Colours and contrast | `plugins/blixis-blocks/inc/tokens/color.php` | `parse_color()`, `color_valid()`, `to_srgb()`, `contrast_ratio()` |
| Colour scheme setting | `plugins/blixis-blocks/inc/tokens/scheme.php` | `scheme_get()`, `scheme_save()` (checks `edit_theme_options`), the `blixis_color_scheme` option |
| Stylesheet generator | `plugins/blixis-blocks/inc/tokens/css.php` | `generate_css($config, $scheme)`, `css_variables($config, $dark)`, `config_hash()`, `css_cache_key($config, $scheme)`. The only production generator |
| theme.json projection | `plugins/blixis-blocks/inc/tokens/theme-json.php` | From task 02-03 |
| Client validator | `packages/tokens` (`@blixis/tokens`) | `validateBytes()` and `validateText()` with the same results as PHP, `migrateConfig()`, `parseColor()`, `isColor()`, `toSrgb()`, `contrastRatio()`, and `previewProperties(config, map, scheme)` for `style.setProperty` in the admin preview (`scheme` is `"light"` or `"dark"`). It does not generate stylesheets |

Both validators read a copy of [`token-map.json`](../contracts/tokens/v2/token-map.json) that ships with them; the copies and the contract file are generated by `packages/tokens/scripts/build-contract.ts` and a test keeps them byte-identical. The map also carries the units and slider ranges the setup wizard's controls read (`fields`, `shadowControls`). The theme.json projection uses the same map and value rules instead of its own copy. The PHP code uses no WordPress functions, so the same files run in WordPress and in plain PHP.

## Guarantees

- Unknown names, missing sections, wrong types, values outside each grammar, a different breakpoint set, configs over 64 KiB or nested deeper than 8, and invalid JSON are refused, with the error codes in the contract.
- CSS injection attempts (`;`, `}`, `</style>`, comments, `url()`, `expression()`, `@import`, `var()` smuggling, control characters, and Unicode tricks) fail validation, so they never reach the generator.
- Hex colours are normalized (lower case, short hex expanded), so the config hash does not depend on spelling. `rgb()`, `hsl()`, and `oklch()` keep the entered text, and component ranges are enforced (`rgb(256 0 0)` is refused).
- A stored version 1 config is read under the version 1 rules and migrated to version 2 on read and on save; nothing is lost and the rollback target is migrated too.
- Generated output is byte-stable: the same config gives the same stylesheet and cache key on PHP 8.3, 8.4, and 8.5.

## Applying tokens

Task [03-05](../roadmap/phases/03-child-theme-setup-wizard/05-token-preview-persistence.md) adds `plugins/blixis-blocks/inc/tokens/apply.php`.

- **Effective config.** The stored config, revalidated and hash-checked on every read. If it does not validate, its previous config; if that does not validate either, nothing, and Base presets apply. A config applies only while its `theme.slug` is the active stylesheet.
- **Delivery.** The `wp_theme_json_data_theme` filter merges the [theme.json projection](THEME_JSON_BRIDGE.md), so WordPress generates the `--wp--preset--*` variables for the site and the editor. With a dark palette the colour presets are `var(--blixis-color-*)` so blocks follow the scheme. An inline `blixis-tokens` stylesheet carries the `--blixis-*` properties (and the dark ones under `prefers-color-scheme` according to the site's colour scheme setting), and the chosen Font Library families are printed as local `@font-face` rules ([local fonts](FONTS.md)).
- **Cache invalidation.** Every save and rollback fires `blixis_tokens_saved`, which clears WordPress's theme.json caches so the next request sees the new values, and then `blixis_tokens_changed`, where page caches should purge.
- **Rollback.** `store_rollback()` writes the previous config as a new revision with compare-and-swap; the replaced config becomes the new previous one, so a rollback can be undone.
- **Site Editor policy.** User-origin (Site Editor) theme presets for colours, font families, font sizes, spacing, radius, and shadows, and the content and wide widths, are removed while a Blixis config applies. Other user settings, such as custom colours, are kept.
- **Preview.** `?blixis_preview=<nonce>` applies the requesting user's wizard draft, only for a logged-in user with `edit_theme_options` and a valid nonce bound to that user. Preview responses send `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`, and a robots `noindex` meta tag. Anyone else gets the normal page. The wizard shows it in an iframe with 390, 820, and 1280 px widths that never change stored values.

**Limit:** Base uses token presets for the page background and text colour; its templates do not yet use the font, link, or spacing presets, so the preview of a neutral Base page shows few changes and a body font needs a style reference in the child theme's `theme.json`. Task [03-06](../roadmap/phases/03-child-theme-setup-wizard/06-token-driven-themes.md) Part A closes this; Part B added colour formats and dark mode; Part C adds friendlier wizard controls.

## Dark mode and colour formats

`colorsDark` is an optional second palette. The site setting `blixis_color_scheme` (`system` by default, `light`, `dark`; `scheme_save()` needs `edit_theme_options`) decides how it is used; it has no effect without a palette and there is no visitor toggle. The contract has the exact rules for [colour formats](../contracts/tokens/README.md#colours), [the dark palette](../contracts/tokens/README.md#dark-palette), [units and slider ranges](../contracts/tokens/README.md#units-and-slider-ranges), and [migration](../contracts/tokens/README.md#migration). The wizard's colour pickers and side-by-side palettes arrive with Part C of task 03-06; the current wizard accepts every format and a submitted `colorsDark` and validates them on the server.

## Tailwind CSS and the Site Editor

The Site Editor (Appearance → Editor) styles with WordPress global styles: `theme.json` presets become CSS custom properties such as `--wp--preset--color--primary`, and its controls never write Tailwind classes. Blixis fills those presets from the tokens, so the editor offers the wizard's colours, fonts, and sizes. Blixis Base also loads its compiled Tailwind v4 utilities into the editor (`add_editor_style`, task 02-02), so Base template parts that use them look the same in the editor; that build holds only `var(--blixis-*)` references, no values. Arbitrary Tailwind classes typed by users are not supported, by design ([ADR-002](../architecture/decisions/ADR-002-tailwind-token-model.md)).

`bash tests/03-05/run.sh --browsers chromium,firefox` covers this (and, in `tests/03-05/check-v2.php`, v1 migration on read and save, colour formats through global styles, dark mode CSS and presets, and the scheme setting with its capability checks) on disposable WordPress 7.1.4/PHP 8.3 and 7.0.8/PHP 8.5; CI runs it in the required `setup-wizard` job.
